# Dummy Data Guide — Asset Allocation Recommender

Every fixture here lives at `/shared/fixtures/` in the repo (same location referenced
throughout `CLAUDE.md`). It exists so **all five people can start coding today**, in parallel,
without a single one of them waiting on another module's real implementation. Drop this whole
`shared/` folder into the repo root and each person copies what they need into their own
module's `mocks/`, `tests/fixtures/`, or `src/mocks/` folder.

**One rule that makes this work:** everyone's dummy data is keyed to the same 13-instrument
universe in `universe.yaml`. Nobody invents their own ticker list. That's the only piece of
coordination required — everything else below is copy-paste-and-go.

---

## File-by-file map

| File | What it is | Format |
|---|---|---|
| `universe.yaml` | The canonical 13 instruments (8 stocks, 5 MFs) + 4 FD banks everyone's dummy data uses | YAML |
| `fd_rates.json` | Static FD rate lookup, copied from the original synopsis §3.5 | JSON |
| `kpi_thresholds.json` | The actual badge threshold rules (>10% margin = "Healthy", etc.) | JSON |
| `user_profiles.json` | 3 example `UserProfile` payloads (conservative/moderate/aggressive) | JSON |
| `raw_fundamentals.json` | Raw per-stock financial figures, as if freshly fetched from a data source | JSON |
| `stock_fundamentals.json` | The same 8 stocks, already run through the KPI thresholds into full `StockFundamentals` (26 badged `KpiCard`s each) | JSON |
| `mf_holdings.json` | `MfHoldingsBreakdown` for all 5 MF schemes, standing in for the MoneyControl scraper | JSON |
| `allocation_explanations.json` | A full `POST /allocate` response (allocation + stock weights + MF weights) for each of the 3 example profiles | JSON |
| `generate_synthetic_prices.py` | Deterministic script that generates 300 days of fake OHLCV/NAV history for all 13 instruments | Python |
| `prices/*.csv` | Pre-generated output of the script above — ready to use, no setup needed | CSV |
| `correlation_test/CORR_A.csv` `CORR_B.csv` `CORR_C.csv` | Purpose-built price series where A/B correlate at 0.99 and A/C at 0.06 | CSV |
| `chat/chat_messages_fixture.json` | 26 example NL messages (clear / ambiguous / adversarial) with expected `ChatIntent` — Phase 2 | JSON |
| `chat/chat_and_rebalance_responses.json` | Full `POST /chat` and `GET /rebalance-check` response examples — Phase 2 | JSON |

## Per-module usage (Phase 1)

### M1 — Frontend
Copy directly into `src/mocks/`:
- `user_profiles.json` → drives the intake form's "test with a sample profile" path
- `allocation_explanations.json` → the dashboard pie chart, return range, and risk meter
- `stock_fundamentals.json` → the stock detail accordion (all 26 KPI cards, already badged)
- `mf_holdings.json` → the MF holdings pie chart

You need **zero** other module running. `npm run dev -- --mock` should read these four files and
render the complete Phase 1 flow.

### M2 — Forecaster & Optimizer
You don't need anyone's mock output — you need **inputs** to feed your own functions:
- Run `generate_synthetic_prices.py` (or just use the pre-generated `prices/*.csv`) to get
  `price_histories: dict[str, pd.Series]` — load each CSV's `close`/`nav` column, keyed by
  filename-minus-extension, and that dict is exactly what `forecast_universe()` expects.
- For testing `optimize()` in isolation (without chaining through your own `forecast_universe()`
  first), fabricate a `mu_post_tax` dict directly — e.g. `{"TCS.NS": 0.11, "INFY.NS": 0.09, ...}`
  — or derive one by hand-applying the tax formula in `CLAUDE.md` §3.1.1 to a couple of the
  `forecast_universe()` outputs you already have.
- Sanity-check your own optimizer's output shape against `allocation_explanations.json` — same
  `AllocationExplanation` + `InstrumentWeight[]` structure, even though your actual numbers will
  differ since these were hand-set, not computed.

### M3 — Backend API, Schemas, Tax Engine, Fundamentals
- Use `raw_fundamentals.json` as the **input** to your `fundamentals_formatter.py`, and
  `stock_fundamentals.json` as the **expected output** — if your formatter doesn't reproduce
  (or closely match) this file when given the same input and the same `kpi_thresholds.json`,
  something's off. This pairing was generated by one script (`generate_stock_fundamentals.py`,
  included here) precisely so you have a correctness check without needing anyone else's code.
- Stub your mock `/allocate` handler to just return the matching entry from
  `allocation_explanations.json` keyed by profile, until M2/M4/M5 are ready to wire in for real.
- Stub your mock `/fundamentals/{ticker}` and `/mf-holdings/{scheme}` handlers to return directly
  from `stock_fundamentals.json` / `mf_holdings.json`.

### M4 — Universe Selector (Phase 1 scope)
- Use `prices/*.csv` as your mocked `cache_manager.get_prices()` return values — load a CSV,
  return the `close`/`nav` column as a `pd.Series`, and your `select_universe()` never needs the
  real M5 running.
- Use `correlation_test/CORR_A.csv`, `CORR_B.csv`, `CORR_C.csv` for your dedup unit test
  specifically — they're constructed so A-vs-B correlation is 0.99 (must trigger dedup) and
  A-vs-C is 0.06 (must not). The exact correlation values are recorded in `prices/manifest.json`
  under `correlation_test_set` so your test assertions don't have to hardcode a fragile number.
- Use `raw_fundamentals.json` (or `stock_fundamentals.json`) as your fundamentals tiebreaker
  input when two instruments are highly correlated.

### M5 — Data Caching & Scraping
- `raw_fundamentals.json` is the exact return shape your `cache_manager.get_fundamentals()`
  should produce once your real yfinance wrapper is built — build toward this shape.
- `mf_holdings.json` is the exact return shape your `cache_manager.get_mf_holdings()` should
  produce once your real MoneyControl scraper is built.
- `prices/*.csv` / `generate_synthetic_prices.py` double as your own `--use-cache-fixtures`
  backing data — point your fixture-mode `get_prices()` at this folder instead of hitting
  yfinance/mfapi in tests.
- `fd_rates.json` is your literal `data/fd_rates.json` — copy it in as-is.

## Per-module usage (Phase 2 — build only after Phase 1 ships)

### M4 — Chatbot
- `chat/chat_messages_fixture.json` is your entire precision test suite: 15 clear commands,
  5 ambiguous messages that must resolve to `clarify`, and 6 adversarial/contradictory messages
  that must also resolve to `clarify`. Run these through your `intent_extractor.py` (mocking the
  Ollama call at first if you want to test your *validation* logic before the model is wired up)
  and report your pass rate exactly as `CLAUDE.md` §10 and the Phase 2 M4 prompt ask for.

### M3 — /chat, /rebalance-check, persistence
- `chat/chat_and_rebalance_responses.json` shows the exact response shape expected for both a
  successful `adjust_allocation` call and a `clarify` fallback, plus both a drifted and a
  not-drifted `/rebalance-check` result. Use these as your stub responses before wiring in the
  real M4/M2 calls, and as a shape reference once you do.

### M1 — Chat UI
- Both files in `chat/` drop directly into `src/mocks/` alongside your Phase 1 fixtures. The
  `diff_summary` field in each chat response is exactly what your diff view should render.

## Regenerating or extending the data

Everything under `prices/` and `correlation_test/` was produced by
`python3 generate_synthetic_prices.py --out ./prices --days 300`, and
`raw_fundamentals.json` + `stock_fundamentals.json` by `python3 generate_stock_fundamentals.py`
(run from inside this folder, since it reads `kpi_thresholds.json` via a relative path). Both
scripts are **fully deterministic** — anyone who reruns them gets byte-identical output, on any
machine. If you need a 14th instrument or a longer price history, edit the `STOCK_PARAMS` /
`MF_PARAMS` dicts or the `--days` flag and rerun; you do not need to ask anyone else to
regenerate anything on their end, because the recipe (not a shared file) is what stays in sync.

One deliberate technical note, since it matters if anyone later worries about exact
reproducibility: `generate_synthetic_prices.py` seeds via `hashlib.md5`, not Python's built-in
`hash()`. `forecaster.py` (the real, locked module) *does* use built-in `hash()` for its
per-instrument seeding, which is fine for decorrelating instruments within a single run but is
**not** guaranteed identical run-to-run or machine-to-machine unless `PYTHONHASHSEED` is fixed
in the environment. That's a `forecaster.py`/M2 concern, not a bug in these fixtures — flagging
it here so nobody spends an afternoon confused about why their forecast numbers don't match a
teammate's on a different machine.
